# Fingerprint regression — reuploaded original images (31 October 2026)

**Hardware:** Realme 7 Pro RMX2170, MelloDerp Android 14. **Status: no confirmed root cause or hardware-tested fix.**

## Reproducible image comparison

Examined these *freshly reuploaded* packages:
- `ShadowBladeX-perf-Stable-2012-20251125-v1.0.4(2).zip` (previously working)
- `part of mello rom original(1).zip` (reference ROM boot)
- experimental AY Shadow v3 ZIP from this conversation

The reuploaded inputs are byte-for-byte the same as the earlier original uploads; original ShadowBladeX `zImage` SHA256 is `e28d56875dc5386f7cefe9d427b3b9513d67c17acc87b65048521da31f82f8ee` and the Mello ROM `boot.img` SHA256 is `17e004d64cecd1363f9514313cc9b9b5d144ae4ef54fd1591a087e0dc026563b`.

Both compressed kernels contain `IKCFG_ST` / `IKCFG_ED`, from which their full compiled `.config` was extracted. Each contained 1,886 set Kconfig entries, of which **77 have different values or are absent in one kernel**.

Fingerprint-specific settings (`CONFIG_OPPO_FINGERPRINT`, `CONFIG_OPPO_FINGERPRINT_FPC`, `CONFIG_OPPO_FINGERPRINT_GOODIX_OPTICAL`, `CONFIG_OPPO_FINGERPRINT_JIIOV_OPTICAL`) are enabled in **both** images. Fingerprint driver source tree SHA also matches between the Mello and ShadowBladeX repositories.

### DTB analysis

The known-working kernel includes 4 DTBs, with hashes (prefixes) in order:
`0711655f, d80bb543, 14cfd64c, 372954f6`.

The AY v3 recovery package used the **stock ROM** DTBs instead:
`0711655f, 14cfd64c, f632f6b3, d80bb543`.

The fourth original custom `372954f6` and stock `f632f6b3` have the same nodes/properties **except for the stock ROM's extra /reserved-memory/ramoops node and corresponding symbol**; the other blobs differ in sequence. The fingerprint-related nodes have not been shown to differ.

## Diagnostic v3.1 package

A local experimental ZIP was generated by combining the EXACT SAME gzip kernel image from the successful AY v3 build with the four appended DTBs **from the known-working ShadowBladeX v1.0.4 kernel**, in original order. Only `zImage`, installer version labels and diagnostic manifest differ. `zImage` SHA256: see `fingerprint-test-sha256.txt` in the ZIP.

This is a **controlled test**, not a confirmed repair. It does NOT revert the 77 kernel configuration changes. Flashing may still lead to a bootloop or other device problems.

## Safe next diagnosis

1. Preserve current Boot partition backup before testing and ensure OrangeFox can restore it.
2. Test whether enrolling a new fingerprint is blocked vs just unlocking; do not delete existing templates.
3. Try disabling kernelSU modules temporarily (reversible) if suspected.
4. If fingerprint still fails with DTB-only test, restore **previously working v2.1 boot/kernel** and verify fingerprint; do not touch persist/vendor or wipe data.
5. Collect sanitized `dumpsys fingerprint` and fingerprint HAL `logcat` traces. Isolate source/config/kernel-root-hook changes only after confirmed v3-only regression.

Do not confuse a successful kernel compile, ZIP CRC or DTB parse with an on-device fingerprint test. SELinux was shown as Permissive in AY v3; the root cause of that state is not established.
